# V1 报表规则与统计口径

本文档是《子午花信》V1 `reportService` 和 `reportAggregator` 的唯一统计依据。

所有周报、月报、年报必须按本文档口径生成。页面层禁止自行计算报表、拼接报表、累计打卡流水或合并同名习惯。

## 1. 报表系统目标

V1 报表系统只解决个人修习记录的稳定复盘问题。

周报用于回答：

- 本周哪些天完成了修习。
- 每个习惯在 7 天内的完成状态。
- 本周完成率、累计修习、坚持时日和最长连日是否可信。

月报用于回答：

- 本月每日修习状态如何分布。
- 哪些习惯在本月稳定坚持，哪些中断较多。
- 本月完成率和趋势是否能反映真实坚持情况。

年报用于回答：

- 全年修习热力分布。
- 年累计修习和坚持趋势。
- 长周期内的活跃月份、低谷月份和整体坚持节奏。

报表系统不负责生成医疗建议，不负责 AI 结论，不负责社交排名，也不负责直接修正用户数据。

## 2. 报表数据来源

V1 报表必须来自以下三类核心数据：

- `userHabit`：用户习惯实例，定义某次添加内置习惯后的生命周期。
- `policyVersion`：习惯策略版本，定义某个 `userHabitId` 在某段时间内的应修规则。
- `dailyCheckinState`：每日最终状态，定义某个 `userHabitId` 在某个自然日的最终打卡结果。

报表可以辅助读取：

- `builtInHabit`：补充习惯名称、分类、图标、主题。
- 自定义 `userHabit` 元信息：当 `source = custom` 或 `habitId` 为 `custom_...` 时，名称、分类、主题和备注以该用户自己的 `userHabit` / `user_habits` 字段为准。
- 锁定状态或锁定快照：处理删除当天、策略修改当天、低可信日期等特殊口径。
- `cacheMeta` / `reportVersion`：判断报表缓存是否有效。

报表不得直接以以下数据作为统计事实源：

- 旧 `checkin_logs`。
- 旧 `CheckinLogs`。
- `checkin_operations` 原始流水的简单累计结果。
- 页面临时状态。
- 习惯名称或 `habitId` 聚合后的粗粒度记录。

自定义修习的 `habitId` 是用户私有目录 ID，仅用于把同一个自定义修习的多个生命周期聚合展示；它不得替代 `userHabitId` 做生命周期计算，也不得写入官方内置习惯库。

自定义修习停用后，custom `habitId` 对应的用户私有目录条目仍可保留在自定义习惯库中；再次启用时必须生成新的 `userHabitId`，旧 `userHabitId` 保持删除状态并继续作为历史报表事实源之一。

自定义修习名称变化必须区分两种意图：仅修改名称时原 `userHabitId` 和历史报表连续记录保持不变；作为新习惯时旧 `userHabitId` 软删除，新名称创建新的 custom `habitId` / `userHabitId`，旧历史继续归属旧名称。

空名 custom 属于未上线测试污染数据，不进入报表展示；清理时可删除其本地和云端关联策略、状态和操作记录。

`checkin_operations` 只用于同步、审计、冲突排查和生成 `dailyCheckinState`。首页和报表优先读取 `dailyCheckinState`。

## 3. 业务日期规则

所有报表日期必须统一走 `TimeService`。

统一口径：

- 时区：`Asia/Shanghai`。
- 自然日：中国时区 00:00:00 到 23:59:59。
- 自然周：周一开始，周日结束。
- 自然月：公历自然月第一天到最后一天。
- 自然年：公历自然年 1 月 1 日到 12 月 31 日。

报表周期生成必须使用：

- `timeService.getWeekRange(date)`
- `timeService.getMonthRange(date)`
- `timeService.getYearRange(date)`
- `timeService.isFutureDate(date)`
- `timeService.getTodayKey()`

农历只用于副文案展示，不参与以下计算：

- 应修判定。
- 分母。
- 分子。
- 完成率。
- 累计修习。
- 坚持时日。
- 最长连日。
- 周/月/年趋势。

## 4. 今日应修判定规则

“应修”是指某个 `userHabitId` 在某个自然日应被计入报表分母。

判定输入：

- `userHabit`
- 命中日期 `date`
- 该日期有效的 `policyVersion`
- 该日期的 `dailyCheckinState`
- 锁定状态或锁定快照
- `todayKey`

基础判定顺序：

1. 如果 `date` 是未来日期，结果为 `not_required`，不计分母。
2. 如果存在锁定状态，优先使用锁定状态。
3. 如果没有命中 `policyVersion`，结果为 `not_required`。
4. 如果 `date` 早于策略 `effectiveStartDate` 或 `startDate`，结果为 `not_required`。
5. 如果 `date` 晚于策略 `effectiveEndDate`，结果为 `not_required`。
6. 如果 `userHabit` 已删除，删除日之后结果为 `not_required`；删除当天按删除当天规则处理。
7. 其余情况按频次规则判断是否应修。

每天频次：

- 从策略开始日期起，每个非未来自然日都属于应修。
- 删除日之后不属于应修。
- 策略结束日之后不属于应修。

每周固定星期：

- `frequencyConfig.weekdays` 定义应修星期。
- 星期计算必须基于 `Asia/Shanghai`。
- 推荐内部统一为周一 `1` 到周日 `7`。
- 仅当 `date` 的星期命中配置时属于应修。

间隔天数：

- `frequencyConfig.intervalDays` 必须是大于等于 1 的整数。
- 锚定日期为该策略版本的 `effectiveStartDate`，没有则使用 `startDate`。
- 如果 `date < anchorDate`，不属于应修。
- 如果 `diffDays(date, anchorDate) % intervalDays === 0`，属于应修。
- 策略变更后，新策略版本从新 `effectiveStartDate` 重新锚定。

V1 不要求为报表周期内每一天提前物理写入应修快照。缺失日期可以由 `reportService` 根据策略版本即时推导，但删除当天、策略修改当天、低可信日期等特殊口径必须可锁定、可解释。

## 5. 打卡状态规则

`dailyCheckinState.status` 必须使用统一枚举：

- `checked`
- `canceled`
- `unchecked`
- `not_required`

状态口径：

| 状态 | 是否计入分母 | 是否计入完成 | UI 展示 | 报表展示 |
|---|---:|---:|---|---|
| `checked` | 是 | 是 | 完成态 | 已完成 |
| `canceled` | 视应修规则而定 | 否 | 待完成或已取消态 | 应修未完成，特殊日可不计分母 |
| `unchecked` | 视应修规则而定 | 否 | 待完成态 | 应修未完成 |
| `not_required` | 否 | 否 | 不展示或弱化展示 | 非应修日 |

普通应修日：

- `checked`：分母 +1，分子 +1。
- `canceled`：分母 +1，分子 +0。
- `unchecked`：分母 +1，分子 +0。
- `not_required`：分母 +0，分子 +0。

特殊日：

- 删除当天未打卡：分母 +0，分子 +0。
- 删除当天已打卡且最终仍为 `checked`：分母 +1，分子 +1。
- 删除当天已打卡后又取消：分母 +0，分子 +0。
- 策略修改当天最终状态为 `checked`：分母 +1，分子 +1。
- 策略修改当天最终状态为 `canceled`、`unchecked` 或 `not_required`：分母 +0，分子 +0。
- 低可信日期：默认不计入分母和分子。

## 6. 删除当天规则

删除习惯必须是软删除，历史数据必须保留。

删除前已打卡：

- 如果删除当天最终状态仍为 `checked`，该日计入分母和分子。
- 首页可临时保留已完成状态和取消入口。
- 报表展示为已完成。
- 锁定原因建议记录为 `deleted_after_checkin`。

删除前已打卡，但删除后用户又取消当日打卡：

- 最终状态以取消后的 `dailyCheckinState` 为准。
- 该日不计入分母和分子。
- 首页移除该习惯。
- 报表展示为非应修或不展示完成。

删除前未打卡：

- 删除当天不计入分母。
- 删除当天不计入分子。
- 首页立即移除该习惯。
- 报表展示为非应修日。
- 锁定原因建议记录为 `deleted_without_checkin`。

删除前存在应修但未打卡的历史日：

- 删除日之前的普通应修日必须保留真实历史。
- 未打卡历史日按 `unchecked` 展示，计入分母，不计入分子。
- 观心周点阵展示为主题描边状态，不得因该习惯后来软删除且无 `checked` 记录而隐藏整条习惯行。
- 仅当天创建、当天未打卡、当天删除且没有删除前历史应修日时，可以按低压力口径不展示压力行。

删除日之后：

- 不再计入分母。
- 不再展示为当前应修任务。
- 历史周期内仍可展示删除前的有效记录。

## 7. 策略修改当天规则

落地状态：

- V1 新数据链路已落地。
- 本地 service、报表聚合、pending 同步、云端 `daily_checkin_states` 写入、`recoverData` 恢复均应保留 `hasPolicyChangedToday`、`lockedReason` 或兼容字段 `lockReason`。
- 旧数据不做强制 migration；缺少锁定字段的历史记录继续按策略版本和每日最终状态兼容推导，避免误伤历史报表。
- 后续如引入统一 `reportCache`，策略修改、打卡和取消必须触发报表缓存失效。

策略修改必须生成新的 `policyVersion`，并关闭旧策略版本。目标分钟数、频次和开始日期任一变化都属于策略修改。

V1 采用“当天最终状态 + 最新策略命中”口径：

- 历史不重算。
- 修改当天单独处理：如果最新策略命中当天应修，则未完成状态也计入分母。
- 未来按最后一次保存成功的新策略计算。
- 同一个习惯在 UI 和报表中仍展示为一个习惯，不按策略版本拆成多条。

报表计算策略修改当天时，必须先判断 `dailyCheckinState.lockReason` 或等价锁定快照字段 `lockedReason`：

| 锁定原因 | 触发条件 | 分母 | 分子 |
|---|---|---:|---:|
| `strategy_changed_after_checkin` | 当天发生过策略修改，且最终状态为 `checked` | 1 | 1 |
| `strategy_changed_without_checkin` | 当天发生过策略修改，最终状态为 `canceled`、`unchecked` 或 `not_required`，且最新策略当天不应修 | 0 | 0 |
| `strategy_changed_without_checkin` | 当天发生过策略修改，最终状态为 `canceled`、`unchecked` 或 `not_required`，且最新策略当天仍应修 | 1 | 0 |

如果当天发生过策略修改但缺少锁定原因，`reportService` 必须根据 `dailyCheckinState.hasPolicyChangedToday` 和最终 `status` 稳定推导同一口径，并写入 `reportDebugLogs` 说明推导原因。

典型场景：

- 未打卡，直接修改策略：若最后一次保存成功的新策略当天仍应修，分母 1，分子 0；若新策略当天不应修，分母 0，分子 0。
- 先打卡，再修改策略：最终状态为 `checked` 时，分母 1，分子 1。
- 先修改策略，再打卡：最终状态为 `checked` 时，分母 1，分子 1。
- 先打卡，再修改策略，最后取消打卡：最终状态为 `canceled`；若最后一次保存成功的新策略当天仍应修，分母 1，分子 0；若新策略当天不应修，分母 0，分子 0。
- 没有修改策略，只是打卡后取消：不使用策略修改锁定口径，按原本今日是否应修判断分母，最终状态为取消时分子为 0。

同一天多次修改策略：

- 每次保存策略都可以生成新的 `policyVersion`。
- 同一天最终以后续使用的策略，以最后一次保存成功的策略为准。
- 首页和未来报表按最后一次保存成功的策略生成。
- 报表不因同一天多次修改拆成多条习惯轨迹。

同一天多次打卡或取消：

- 每次打卡和取消都生成 `checkinOperation`。
- 操作流水用于同步、审计和问题排查。
- 首页和报表只读取 `dailyCheckinState` 的最终状态。
- 最后是打卡则今天算完成；最后是取消则今天不算完成。

首页“已坚持 X 天”：

- 按当前卡片对应的 `habitId` 长期累计所有生命周期内的有效完成自然日。
- 删除后重新添加同一习惯时，旧 `userHabitId` 的有效完成自然日继续计入。
- 同一自然日内，同一 `habitId` 下多个 `userHabitId` 同时完成时，只计 1 天。
- 同一 `userHabitId + date` 必须先归并为最终 `dailyCheckinState`，只有最终 `status=checked` 才计入。
- `canceled`、`unchecked`、`not_required`、`dateConfidence=low` 不计入。
- 页面层不得自行计算该指标，只能渲染 service 返回的视图模型。

策略修改日之后：

- 报表按新 `policyVersion` 判定应修。
- 间隔天数策略从新策略生效日重新锚定。

## 8. 多生命周期聚合规则

同一个 `habitId` 可以对应多个 `userHabitId`。这通常发生在用户删除某个内置习惯后，又重新添加同一内置习惯。

基本原则：

- 计算必须先按 `userHabitId` 独立完成。
- 展示可以按 `habitId` 聚合。
- 不允许直接用 `habitId` 做生命周期边界。
- 不允许把旧生命周期的策略版本套到新生命周期上。
- 不允许把新生命周期的打卡状态回填到旧生命周期。

聚合方式：

- 分母：同一 `habitId` 下所有相关 `userHabitId` 在周期内的有效应修次数之和。
- 分子：同一 `habitId` 下所有相关 `userHabitId` 在周期内的有效完成次数之和。
- 完成率：聚合分子 / 聚合分母。
- 累计修习：聚合分子。
- 展示名称、图标、主题优先来自 `builtInHabit`，缺失时使用历史快照或兜底文案。

同一自然日内多个生命周期同时存在时：

- 若多个 `userHabitId` 均应修，则分母按实例数累加。
- 若其中一部分完成，日状态可标记为 `partial` 或“部分完成”。
- 若全部应修实例完成，日状态标记为 `checked`。
- 若存在应修但无完成，日状态标记为 `unchecked`。
- 若全部非应修，日状态标记为 `not_required`。

V1 展示可以合并为同一习惯卡片，但调试日志必须能追踪到每个 `userHabitId` 的分子、分母和策略版本命中结果。

展示排序：

- 首页今日习惯卡片按习惯名称首字母或中文拼音顺序展示。
- 观心周报按习惯名称首字母或中文拼音顺序展示。
- 观心月报、年报按周期内打卡次数降序展示；次数相同时按习惯名称顺序兜底。
- 排序只影响 ViewModel 展示顺序，不改变分母、分子、完成率、streak 或多生命周期聚合口径。

## 9. 周报规则

周报周期：

- 自然周，周一开始，周日结束。
- 周期由 `timeService.getWeekRange(date)` 生成。

周报分母：

- 周期内每个非未来日期、每个 `userHabitId` 的有效应修次数之和。
- `not_required` 不计入分母。
- `dateConfidence=low` 默认不计入分母。

周报分子：

- 周期内最终状态为有效 `checked` 的次数之和。
- 已取消、未完成、非应修、低可信待处理不计入分子。

周完成率：

```text
weeklyCompletionRate = weeklyDoneCount / weeklyDueCount
```

当 `weeklyDueCount = 0` 时：

- 完成率显示为 0 或空状态。
- 不显示异常值。
- 不得出现除零错误。

周 streak：

- 在周周期内按自然日计算最长连续完成天数。
- 某一天至少完成一项有效应修，则该日可计为完成日。
- 非应修日不主动打断 streak，但也不增加 streak。
- 未来日期不参与 streak。
- 低可信日期不参与 streak。

周点阵：

- 横向 7 天。
- 每个习惯按 `habitId` 聚合展示，内部按 `userHabitId` 计算。
- 单元格状态至少包括：已完成、应修未完成、非应修、未来、部分完成、低可信待处理。
- 农历只可作为副文案，不参与点阵状态计算。

## 10. 月报规则

月报周期：

- 公历自然月。
- 周期由 `timeService.getMonthRange(date)` 生成。

月历状态：

- 月历按自然日展示。
- 每一天汇总当天所有有效 `userHabitId` 的应修和完成情况。
- 当天无应修：`not_required`。
- 当天有应修且全部完成：`checked`。
- 当天有应修且部分完成：`partial`。
- 当天有应修且均未完成：`unchecked`。
- 当天是未来日期：`future`。
- 当天存在低可信待处理记录：可叠加异常标记，但默认不计入完成率。

月完成率：

```text
monthlyCompletionRate = monthlyDoneCount / monthlyDueCount
```

其中：

- `monthlyDueCount` 为月内所有有效应修次数。
- `monthlyDoneCount` 为月内所有有效完成次数。
- 非应修日、未来日期、低可信待处理记录不计入分母和分子。

月趋势：

- V1 可按周或按日期区间展示趋势。
- 趋势数据必须来自同一套日状态聚合结果。
- 不允许页面层重新累计。
- 趋势中的每个点必须能追溯到起止日期、分母、分子。

## 11. 年报规则

年报周期：

- 公历自然年。
- 周期由 `timeService.getYearRange(date)` 生成。

热力图：

- 年热力图按自然日生成。
- 每个自然日先聚合当天所有有效 `userHabitId` 的状态。
- 热力强度可基于当天完成率或完成次数，但必须在 `reportService` 中统一定义。
- 推荐 V1 使用当天完成率分档：
  - `none`：无应修或未来日期。
  - `low`：有应修，完成率小于 50%。
  - `medium`：完成率大于等于 50% 且小于 100%。
  - `high`：完成率等于 100%。
  - `pending`：仅有低可信待处理记录或同步异常待确认。

年累计：

- 年累计修习 = 年周期内有效完成次数。
- 年应修次数 = 年周期内有效应修次数。
- 年坚持时日 = 年周期内至少完成一项有效修习的自然日数量。
- 年最长连日 = 年周期内自然日维度的最长连续完成天数。

年趋势：

- V1 可按月输出 12 个趋势点。
- 每个趋势点包含该月分母、分子、完成率、完成天数。
- 不要求冷启动一次性下载多年历史数据。
- 当前年以外的历史年数据按需分页加载。

## 12. 未来日期规则

未来日期一律不计入分母。

规则：

- 判断未来日期必须使用 `timeService.isFutureDate(date)`。
- 未来日期不计入应修次数。
- 未来日期不计入完成次数。
- 未来日期不参与 streak。
- 未来日期不参与趋势计算。
- 未来日期在 UI 中可展示为未来态或空态。

即使未来日期按策略推导属于应修，也不得进入当前报表分母。

## 13. 非应修日规则

`not_required` 表示该 `userHabitId` 在该自然日不属于应修。

出现 `not_required` 的常见原因：

- 未到策略开始日期。
- 不符合每周固定星期。
- 不符合间隔天数。
- 策略已结束。
- 删除日之后。
- 删除当天未打卡。
- 策略修改当天最终状态不是 `checked`。
- 未来日期。
- 没有命中有效策略版本。
- 低可信日期待处理时被排除。

规则：

- `not_required` 不计入分母。
- `not_required` 不计入分子。
- `not_required` 不参与完成率。
- `not_required` 不增加 streak。
- `not_required` 默认不作为漏打展示。

## 14. 低可信日期规则

`dateConfidence=low` 表示打卡日期存在明显不确定性，例如离线时客户端时间与服务端时间偏差过大。

V1 处理规则：

- 默认不静默计入报表。
- 不计入分母。
- 不计入分子。
- 不计入累计修习。
- 不计入坚持时日。
- 不计入最长连日。
- 可在报表中展示待处理或同步异常标记。
- 必须保留调试信息，便于后续排查。

数据要求：

- `dailyCheckinState` 或相关异常记录应标记 `dateConfidence=low`。
- `reportDebugLogs` 应记录该记录被排除的原因。
- V1 不要求实现用户确认日期的完整交互。
- V2 可增加用户确认后再纳入报表的能力。

## 15. reportService 禁止事项

页面层禁止：

- 自行计算报表。
- 自行拼接报表。
- 自行计算完成率。
- 自行计算分母。
- 自行计算 streak。
- 自行拼接周点阵。
- 自行拼接月历。
- 自行拼接年热力图。
- 自行合并同名习惯。
- 直接累计 `checkin_logs`。
- 直接累计 `CheckinLogs`。
- 直接累计 `checkin_operations`。
- 直接用 `habitId` 替代 `userHabitId` 计算生命周期。
- 直接使用 `new Date()` 生成报表周期。

`reportService` 禁止：

- 以旧 `checkin_logs` 作为最终事实源。
- 忽略 `policyVersion`。
- 忽略 `userHabitId` 生命周期。
- 把未来日期计入分母。
- 把非应修日计入分母。
- 把低可信日期静默计入报表。
- 在没有明确口径时自行扩展医疗、AI 或社交结论。

修改本文档规则时，必须同步更新：

- `reportService` 测试。
- 删除当天测试。
- 策略修改当天测试。
- 多生命周期聚合测试。
- 缓存失效说明。
- 必要的数据迁移说明。

## 16. 报表测试重点

必须覆盖以下边界测试：

基础周期：

- 周报以周一开始、周日结束。
- 月报覆盖自然月第一天到最后一天。
- 年报覆盖 1 月 1 日到 12 月 31 日。
- 农历副文案不影响任何统计结果。

频次规则：

- 每天频次从开始日起每日应修。
- 每周固定星期只在命中星期应修。
- 间隔天数从锚定日开始计算。
- 间隔天数策略修改后重新锚定。

状态规则：

- `checked` 计入分母和分子。
- `unchecked` 计入分母不计分子。
- `canceled` 在普通应修日计入分母不计分子。
- `not_required` 不计入分母和分子。

特殊口径：

- 删除当天已打卡计入分母和分子。
- 删除当天未打卡不计入分母和分子。
- 删除当天已打卡后取消，不计入分母和分子。
- 策略修改当天最终状态为 `checked`，计入分母和分子。
- 策略修改当天最终状态为 `canceled`、`unchecked` 或 `not_required`，不计入分母和分子。
- 策略修改当天已打卡后取消，不计入分母和分子。

多生命周期：

- 同一 `habitId` 删除后重加生成多个 `userHabitId`。
- 新旧生命周期策略不混用。
- 新旧生命周期打卡不混算。
- 展示可按 `habitId` 聚合。
- 聚合分母等于各 `userHabitId` 分母之和。
- 聚合分子等于各 `userHabitId` 分子之和。

未来和异常：

- 未来日期不计分母。
- 未到开始日期不计分母。
- 删除日之后不计分母。
- `dateConfidence=low` 不计分母和分子。
- 同步失败 pending 状态不会被重复计数。

报表输出：

- 周报 7 天点阵状态正确。
- 月报月历状态正确。
- 年报热力分档正确。
- 周/月/年完成率除零安全。
- 累计修习只统计有效完成次数。
- 坚持时日按自然日去重。
- 最长连日不跨出当前报表周期。

架构边界：

- 页面层不直接调用报表计算工具。
- 页面层不直接累计旧日志。
- 页面层不直接合并同名习惯。
- 报表缓存随打卡、取消、策略修改、删除、跨天刷新失效。
