# V1 产品与技术边界

本文档用于明确《子午花信》V1 的产品边界、技术边界和非目标，防止开发阶段出现需求失控、架构绕行和一期过重。

V1 的判断标准不是“功能多”，而是“个人习惯打卡闭环稳定、数据可恢复、报表可信、异常不阻断”。

## 1. V1 核心目标

V1 只解决一个核心问题：

让用户可以稳定地管理自己的养生修习习惯，并在每日完成打卡后，通过周、月、年报表看到可恢复、可解释、可持续的个人记录。

V1 必须保证：

- 用户清缓存或换设备后，可以从云端恢复用户习惯、策略版本和近期打卡状态。
- 用户进入首页后，可以看到今日应修习惯。
- 用户可以对今日应修习惯打卡和取消打卡。
- 本地操作必须即时反馈，云端同步失败不得阻断继续使用。
- 用户可以在观心页稳定查看周、月、年报表。
- 删除当天、策略修改当天、低可信日期、同步失败等异常状态必须可见、可解释、可降级。

V1 不追求完整社交、课程、内容消费、医疗建议或复杂多端协同。任何新增能力都不得破坏打卡、取消打卡、恢复和报表主链路。

## 2. V1 核心闭环

V1 的核心闭环如下：

```text
用户进入小程序
  -> login 获取 openid 和服务端时间
  -> 读取本地缓存
  -> 必要时从 CloudBase recoverData
  -> migrationService 补齐字段和版本
  -> 首页生成今日应修任务
  -> 用户打卡或取消打卡
  -> 本地 dailyCheckinState 乐观更新
  -> 生成 checkinOperation 并进入同步队列
  -> syncService 同步到云端
  -> reportService 基于策略版本和最终状态生成周/月/年报表
```

页面只渲染这个闭环的结果，不直接承担缓存、云函数、打卡状态、报表口径或时间口径计算。

## 3. V1 必做功能

### 3.1 首页：案台

核心职责：

- 承接用户每日进入后的第一使用场景。
- 展示当前时辰信息、今日修习进度和今日应修习惯。
- 提供打卡和取消打卡入口。

必须实现内容：

- 加载 service 返回的今日习惯列表。
- 展示今日完成数、总数和进度。
- 今日无习惯时展示空状态，并引导进入修习页。
- 今日习惯超过 12 个时提示用户调整频次或减少今日任务。
- 点击习惯时调用 `checkinService` 完成打卡或取消打卡。
- 展示同步失败、低可信日期、恢复中等非阻断状态。

不应该承载的内容：

- 不直接读写缓存。
- 不直接调用云函数。
- 不直接计算今日应修。
- 不直接计算完成率。
- 不直接拼接策略版本。
- 不直接操作 `dailyCheckinState`。
- 不承载课程、内容 feed、社交推荐或排行榜。

### 3.2 修习页

核心职责：

- 承担内置习惯库浏览和用户习惯管理。
- 支持添加、编辑策略、删除习惯。

必须实现内容：

- 展示“我的”“运动类”“理疗类”“起居类”分类。
- 展示固定 25 个内置习惯。
- 支持一键开始。
- 支持设置目标分钟数、频次、开始日期。
- 支持编辑已有习惯策略。
- 支持软删除用户习惯实例。
- 删除前必须二次确认，并使用危险操作样式。

不应该承载的内容：

- 不允许用户自由创建全新内置习惯。
- 不承载课程体系。
- 不承载复杂推荐系统。
- 不直接生成 `userHabitId` 之外的生命周期混用逻辑。
- 不直接改策略版本状态。
- 不直接写云端集合。

### 3.3 观心页

核心职责：

- 承担周、月、年统计复盘。
- 展示可解释的完成率、累计修习、坚持时日和热力状态。

必须实现内容：

- 支持周报、月报、年报切换。
- 支持周期切换。
- 周报展示 7 天状态。
- 月报展示月历状态。
- 年报展示全年热力状态。
- 已删除但历史周期内存在记录或应修状态的习惯仍可展示。
- 同一 `habitId` 下多个 `userHabitId` 默认可聚合展示，但必须先按 `userHabitId` 独立计算。
- 农历只做副文案展示，不参与报表计算。

不应该承载的内容：

- 不直接计算报表分母。
- 不直接计算完成率。
- 不直接计算 streak。
- 不直接合并同名习惯。
- 不直接推导策略版本。
- 不长期持久化完整报表快照。
- 不承载内容社区或 AI 医疗解释。

### 3.4 归藏页

核心职责：

- 承担用户资料、设置入口和分享入口。
- 作为轻量个人中心，不扩展为社区中心。

必须实现内容：

- 展示头像和昵称。
- 用户拒绝授权时展示默认头像和默认昵称。
- 保留手动设置入口。
- 提供设置、关于、隐私政策等入口。
- 支持分享或复制分享信息。
- 分享和复制不得携带隐私数据。

不应该承载的内容：

- 不展示他人数据。
- 不承载好友关系。
- 不承载排行榜。
- 不承载勋章真实规则体系。
- 不承载复杂账号治理后台。
- 不在前端暴露 DeepSeek API Key。

## 4. V1 数据边界

### 4.1 必须持久化

`userHabit`

- 用户习惯实例必须持久化。
- 每次添加同一内置习惯都必须生成新的 `userHabitId`。
- 自定义习惯的 `habitId` 表示用户私有习惯库条目；停用自定义习惯只结束当前 `userHabitId` 生命周期，不移除该库条目。
- 再次启用同一自定义习惯时必须复用原 custom `habitId` 并生成新的 `userHabitId`，不得复活已删除实例。
- 已添加自定义习惯名称变化时必须让用户选择：仅修改名称则保留原生命周期；作为新习惯则旧实例软删除并创建新的 custom `habitId` / `userHabitId`。
- 空名 custom 数据属于未上线测试污染数据，可以物理清理本地和云端关联事实数据；正式创建链路不得产生空名 custom。
- 自定义习惯库最多保留 12 个有效名称的 custom `habitId` 目录条目，包含已停用但仍显示在自定义库中的条目；同时最多启用 5 个 active 自定义习惯。
- 删除必须软删除，历史生命周期不得丢失。
- `addedAt` 可持久化用户添加习惯的精确时间；它只影响首页未置顶习惯的添加顺序排序，不影响修习策略、打卡状态、报表分母、分子或 streak。
- `pinnedAt` 可持久化首页置顶偏好；它只影响首页排序，不影响修习策略、打卡状态、报表分母、分子或 streak。

`policyVersion`

- 策略版本必须持久化。
- 策略必须归属于 `userHabitId`，不得只按 `habitId` 归属。
- 同一 `userHabitId` 下策略版本时间段不得重叠。

`dailyCheckinState`

- 每日最终状态必须持久化。
- 首页和报表优先读取每日最终状态。
- 打卡和取消都必须更新最终状态。

`checkinOperation`

- V1 必须保留操作流水模型和核心字段。
- V1 可简化复杂乱序归并，但打卡和取消必须生成操作记录。
- 幂等写入必须依赖 `operationId` 和 `idempotencyKey`。

### 4.2 可运行时生成

`reportData`

- 周、月、年报表默认运行时生成。
- 报表由 `userHabit`、`policyVersion`、`dailyCheckinState` 和特殊锁定状态计算得出。
- 不建议 V1 长期持久化完整报表快照。

今日任务视图模型

- `todayHabitList`、`completedCount`、`totalCount`、`progressPercent` 由服务层运行时生成。
- 页面不得自行计算。

### 4.3 可缓存

以下数据可以缓存，但缓存不是事实源：

- 当前用户习惯实例。
- 当前策略版本和近期历史策略版本。
- 近期 `dailyCheckinState`，建议默认覆盖最近 90 天。
- 最近一次周/月/年报表视图模型。
- `cacheMeta`、`cacheVersion`、`dataVersion`、`reportVersion`。

缓存失效必须由 service 统一管理。打卡、取消、添加、编辑策略、删除、跨天刷新、清缓存恢复、migration 后都必须触发相关缓存失效。

### 4.4 不进入 V1

以下数据结构不作为 V1 必须完整落地项：

- 长期报表快照表。
- 全量历史明细冷启动缓存。
- 全年每日应修物理快照完整补齐。
- 完整多端冲突裁决结果表。
- 社交关系数据。
- 排行榜数据。
- 课程学习数据。
- 内容 feed 数据。
- 医疗 AI 咨询记录。

## 5. V1 技术边界

### 5.1 V1 必须做

`TimeService`

- 统一 Asia/Shanghai 业务日期。
- 统一今日 key、周/月/年边界。
- 支持 serverTime 和 dateConfidence。
- 支持跨天刷新。
- 页面层不得直接使用 `new Date()` 计算业务日期。

`reportService`

- 统一生成周/月/年报表。
- 统一处理分子、分母、完成率、streak、日历状态和热力状态。
- 支持删除当天和策略修改当天特殊口径。
- 支持同一 `habitId` 下多个 `userHabitId` 的聚合展示。

`syncService`

- 管理 pending 队列。
- 支持本地乐观更新后的云端同步。
- 支持 retry。
- 支持 syncLogs 和 conflictLogs。
- 服务端确认状态回写本地。

`migrationService`

- 处理旧缓存和旧集合字段兼容。
- 维护 cacheVersion、dataVersion 和 migrationVersion。
- 迁移失败不得导致用户无法进入小程序。

`recoverData`

- 支持清缓存后恢复用户习惯、策略版本和近期每日状态。
- 历史数据按周期分页加载。
- 恢复失败必须可见、可重试、不阻断。

`storageService`

- 统一本地缓存读写。
- 页面不得直接读写业务缓存。

`cloudService`

- 统一云函数调用。
- 页面不得直接调用业务云函数。

`checkinService`

- 统一打卡、取消、操作流水、每日最终状态和同步状态。

`habitService`

- 统一习惯实例、策略版本、添加、编辑、删除和今日任务生成。

### 5.2 V1 不做

V1 不实现：

- 多端复杂离线冲突完整裁决。
- `checkinOperation -> dailyCheckinState` 的复杂乱序归并。
- 冷启动一次性恢复全部历史明细。
- 全量历史报表快照。
- 全年每日应修物理快照完整补齐。
- 重型全局 store 或复杂状态管理框架。
- 复杂 AI 个性化体系。
- AI 医疗建议。
- 复杂账号治理后台。

V1 可以为 V2 保留字段、接口和日志，但不得把这些扩展能力变成一期主链路依赖。

## 6. V1 UI 边界

V1 UI 原则：

- 保留当前 UI 骨架，不整体重做。
- 不新增一套新的视觉体系。
- 不通过架构重构顺手重画页面。

V1 只做局部技术对齐：

- 五主题色 token 化：`t-green`、`t-red`、`t-yellow`、`t-blue`、`t-purple`。
- 旧色收敛到 design token。
- 微信默认危险红 `#e64340` 不再继续使用。
- 删除确认和危险操作统一使用 `--color-danger` 或规范危险色。
- 删除菜单项必须有 `type: danger` 并正确渲染。
- `custom-tab-bar` 是唯一一级导航视觉来源。
- 页面进入时同步 tab selected 状态。
- 优先抽离基础组件：`BaseButton`、`BaseCard`、`BaseTag`、`ConfirmDialog`、`PickerSheet`、`EmptyState`、`LoadingState`。

V1 不做：

- 整站视觉重做。
- 新增营销落地页。
- 新增复杂动效系统。
- 新增与 PRD 无关的内容页面。
- 重做导航结构。

## 7. V1 AI 边界

DeepSeek API 在 V1 中不是主链路能力。

V1 AI 原则：

- DeepSeek 不进入打卡、取消、恢复、同步和报表生成主链路。
- DeepSeek 调用失败不得影响核心功能。
- AI 只允许作为辅助建议、复盘文案或提醒文案。
- AI 文案必须标记为辅助建议，不替代医疗建议。
- DeepSeek API 必须通过 `deepseekProxy` 云函数调用。
- API Key 只允许保存在云函数环境变量中。
- 前端不得出现 API Key。
- AI 调用必须支持限流、缓存和错误兜底。

V1 不做：

- 医疗诊断。
- 医疗处方。
- 强依赖 AI 的习惯推荐。
- AI 驱动的报表结论作为唯一解释。
- AI 聊天入口作为核心功能。

- 打卡竞赛。
- 课程体系。
- 内容 feed。

- 分享裂变。

- 复杂勋章体系。

## 9. V1 成功标准

满足以下条件，才可以认为 V1 稳定上线：

- 新用户首次进入可以看到空状态，并能添加习惯。
- 用户可以通过一键开始添加习惯。
- 用户可以编辑习惯策略。
- 用户可以软删除习惯。
- 首页今日应修习惯展示准确。
- 今日习惯超过 12 个时有调整提示。
- 用户可以打卡、取消打卡、再次打卡。
- 快速重复点击不会产生重复有效状态。
- 本地操作即时反馈。
- 云同步失败时进入 pending，不阻断继续使用。
- 网络恢复后可补同步。
- 清缓存后可以恢复用户习惯、策略版本和近期打卡状态。
- 周报、月报、年报稳定展示。
- 未来日期不计入分母。
- 农历只做展示，不参与报表计算。
- 删除当天已打卡和未打卡口径稳定。
- 策略修改当天已打卡和未打卡口径稳定。
- 同一内置习惯删除后重新添加，新旧 `userHabitId` 生命周期不混算。
- 同一自定义习惯停用后仍保留在自定义库，再次启用生成新的 `userHabitId`。
- 自定义习惯仅改名时历史连续记录不断；作为新习惯时旧历史留在旧名称下，新名称重新开始记录。
- 同一 `habitId` 下多个 `userHabitId` 报表可聚合展示但不混算。
- 低可信日期不会静默污染报表。
- 分享和复制不携带隐私数据。
- DeepSeek 调用失败不影响核心功能。
- 页面层不新增直接缓存、云函数、业务日期和报表计算逻辑。
- 危险色、主题 token 和导航边界完成基础对齐。

## 10. V1 不允许破坏的内容

### 10.1 数据稳定

不允许：

- 用 `habitId` 代替 `userHabitId`。
- 删除习惯时物理删除历史数据。
- 策略版本只按 `habitId` 归属。
- 同一 `userHabitId` 下策略版本时间段重叠。
- 清缓存恢复后混入其他用户数据。
- 本地缓存跨 openid 污染。

必须保证：

- 用户习惯实例生命周期稳定。
- 旧数据可迁移。
- 云端数据按 `_openid` 隔离。
- 删除后历史记录仍可用于报表。

### 10.2 打卡稳定

不允许：

- 取消打卡时物理删除唯一历史依据。
- 重复点击导致重复计数。
- 云端重复提交放大完成次数。
- 页面直接改 `dailyCheckinState`。

必须保证：

- 打卡和取消都生成操作流水。
- 每日最终状态可幂等更新。
- 本地和云端最终状态可对齐。
- 离线操作可 pending 和 retry。

### 10.3 报表稳定

不允许：

- 页面直接计算报表。
- 页面直接合并同名习惯。
- 把未来日期计入分母。
- 把非应修日计入分母。
- 把低可信日期静默计入报表。
- 删除后重加导致新旧生命周期混算。

必须保证：

- 所有报表统一走 `reportService`。
- 报表先按 `userHabitId` 计算，再按 `habitId` 聚合展示。
- 删除当天和策略修改当天口径稳定。
- 农历不参与完成率、累计修习、坚持时日和最长连日计算。

### 10.4 清缓存恢复稳定

不允许：

- 清缓存后只能恢复头像昵称而不能恢复习惯。
- 清缓存后丢失近期打卡状态。
- 恢复失败导致首页无法进入。
- 冷启动强制下载全部历史明细。

必须保证：

- `login` 后通过 `recoverData` 恢复核心数据。
- 近期数据优先恢复。
- 历史数据按需分页。
- 恢复失败可见且可重试。

### 10.5 时间系统稳定

不允许：

- 页面层直接 `new Date()` 计算业务日期。
- 报表、打卡、删除当天、策略修改当天各自使用不同日期口径。
- 跨天后沿用昨日任务。
- 客户端异常时间静默污染报表。

必须保证：

- 所有业务日期统一走 `TimeService`。
- 周/月/年边界统一。
- app 前后台切换和页面 `onShow` 可触发轻量日期校验。
- 低可信日期有标记、有提示、有降级策略。
