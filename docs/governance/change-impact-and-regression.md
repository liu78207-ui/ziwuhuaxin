# 变更影响与回归治理规则

## 1. 目的

本规则用于防止新增功能、局部修改或基础设施调整误伤已经稳定的功能。

治理目标不是承诺“永远不出现缺陷”，而是确保：

- 高风险改动在发布前被正确识别。
- 既有功能有明确的保护清单。
- 事故能够在测试或灰度阶段被拦截。
- 数据类故障能够回滚，不演变为不可恢复的数据损失。

## 2. 总规则

> 任何改动都必须同时证明两件事：新需求已经实现，原有关键链路仍然成立。只证明前者，不允许发布。

对数据和同步链路追加最高红线：

> 未确认归属的数据不得发送，未被服务端确认的操作不得删除，未经完整校验的恢复结果不得覆盖，未经逐条证据确认的正式数据不得修复。

## 3. 变更风险分级

### L1：展示层变更

例如文案、样式、非业务布局调整。

要求：

- 验证目标页面。
- 验证四个主页面基本进入和导航。

### L2：单一业务功能变更

例如新增一个习惯字段、修改一个交互动作。

要求：

- 验证目标功能完整流程。
- 验证它依赖和影响的 service、缓存、同步与报表。
- 验证旧数据兼容。

### L3：公共底座变更

以下模块一律按 L3 处理：

- 环境配置与发布配置。
- 登录、身份、openid 和用户归属。
- `cloudService`、`storageService`、`syncService`。
- `timeService`、migration 和 cache version。
- `recoverData`、清缓存和换设备恢复。
- 云函数公共封装、集合名、索引、权限与数据库规则。
- app 启动、前台恢复和网络恢复顺序。
- 核心数据模型和状态机。

L3 默认影响全产品，不允许由开发者自行降级。

要求：

- 独立提交、独立发布、独立回滚。
- 全量自动化回归。
- 真实环境端到端验证。
- 灰度发布和日志观察。
- 数据备份与明确回滚方案。

## 4. 开工前必须提交变更声明

每次 L2/L3 改动开始前，必须记录：

```text
变更目标：
不允许改变的既有行为：
直接修改模块：
间接依赖模块：
数据模型影响：
缓存影响：
同步影响：
恢复影响：
迁移影响：
环境影响：
最坏故障结果：
回滚方式：
```

“不允许改变的既有行为”必须写成可测试的句子，例如：

- 正式版已有用户升级后仍能看到原习惯和历史打卡。
- 离线打卡在网络恢复后进入正确账号的正式集合。
- 恢复失败时保留原本地数据和 pending。

没有这份声明，不得开始 L3 实施。

## 5. 影响面分析规则

不能只按“修改了哪些文件”判断影响，必须沿依赖链向上下游检查。

例如修改环境配置时，影响链必须至少展开为：

```text
环境识别
  -> 云初始化
  -> 登录身份
  -> 云函数路由
  -> 数据库集合
  -> pending 上传
  -> 云端恢复
  -> 本地缓存替换
  -> 首页和报表
```

链路上的每一项都必须有验证结果。

## 6. 既有功能保护清单

以下能力是 V1 不可破坏链路，每次 L3 发布必须全部通过：

1. 老用户升级后进入。
2. 新用户首次进入。
3. 添加、编辑和删除习惯。
4. 打卡和取消打卡。
5. 离线操作与网络恢复。
6. app 冷启动和回到前台。
7. 清缓存恢复。
8. 换设备恢复。
9. 周报、月报和年报读取。
10. 开发版、体验版和正式版的数据隔离。
11. 旧数据迁移和兼容读取。
12. 同步失败后的重试与人工诊断。

新增功能可以增加保护项，不得删除既有保护项。

## 7. 环境变更专项规则

### 7.1 环境是基础设施，不是普通业务参数

- 环境选择必须集中在唯一配置入口。
- 业务页面和业务 service 不得自行判断集合前缀。
- 当前免费额度约束下，允许开发版、体验版和正式版共用一个 CloudBase 环境。
- 正式版使用无前缀集合，开发版和体验版使用 `test_` 前缀集合。
- 正式和测试必须使用各自固定的云函数入口；入口可以复用业务核心，但集合命名空间必须由服务端入口固定注入。
- 正式云函数入口不得根据普通客户端 payload 中的前缀切换到测试集合，测试入口也不得切换到正式集合。
- 环境隔离应通过新增测试旁路完成，不得为了测试隔离重写已经稳定的正式同步入口。
- 云函数不得信任客户端传入的 openid、任意集合名或可自由变化的前缀来决定数据归属。
- 所有 `test_` 集合必须在客户端发布前完成创建、索引验证和 schema 一致性检查。
- 同一云环境内的集合前缀属于逻辑隔离；不得把它描述成独立云环境级别的物理安全隔离。
- 如果未来具备多个 CloudBase 环境额度，可另行评估物理隔离，但不得因此阻塞当前治理。

### 7.2 本地状态必须同时隔离

所有业务缓存和 pending 必须绑定：

- `ownerUserId`
- `runtimeEnv`
- `cacheVersion`
- `dataVersion`

身份或环境未由云端确认前：

- 可以只读展示本地数据。
- 不得上传 pending。
- 不得执行云端恢复覆盖。
- 不得认领旧环境遗留队列。

### 7.3 环境未准备好不得伪装成空用户

以下情况必须返回不同错误，不能都返回空数组：

- 集合不存在。
- 索引不存在。
- 云函数版本不匹配。
- 权限配置错误。
- 用户确实没有数据。

基础设施未准备好必须阻止发布或进入可诊断降级，不能继续覆盖用户缓存。

## 8. 同步与恢复红线

- operation、最终状态和冲突记录必须在服务端事务中提交。
- 同一业务操作重试必须复用原始 `idempotencyKey`。
- 客户端只有收到相同 operation 的明确确认后，才能把 pending 标记为 `synced`。
- 服务端返回 `STALE` 时，客户端必须采用服务端最终状态，不能只删除本地操作。
- pending 不能因为达到重试次数、重新登录、恢复数据或清缓存而自动消失。
- 恢复必须先完成全部分页、结构校验和唯一键校验，再写入 staging。
- staging 完整提交成功后才能替换正式缓存；任一步失败都必须保留原数据。
- 清缓存前必须确认没有 pending、syncing、retrying 或 failed 操作。

## 9. 测试规则

### 9.1 单元测试不能替代真实链路

L3 发布必须同时具备：

- 单元测试。
- 云函数集成测试。
- 客户端到真实 CloudBase 的端到端测试。
- 真机或开发者工具的升级与恢复测试。

### 9.2 环境矩阵

每个关键场景都必须分别验证：

| 场景 | 开发版 | 体验版 | 正式版 |
|---|---:|---:|---:|
| 登录 | 必测 | 必测 | 必测 |
| 添加习惯 | 必测 | 必测 | 必测 |
| 打卡/取消 | 必测 | 必测 | 必测 |
| pending 重试 | 必测 | 必测 | 必测 |
| 清缓存恢复 | 必测 | 必测 | 必测 |
| 旧版本升级 | 可选 | 必测 | 必测 |
| 数据不跨环境 | 必测 | 必测 | 必测 |

### 9.3 故障注入

同步相关改动必须主动验证：

- 断网。
- 超时。
- 云函数未部署。
- 集合或索引缺失。
- 事务繁忙。
- 重复请求。
- 多设备相反操作。
- app 在同步中途退出。
- 恢复分页中断。
- 本地身份与环境不匹配。

## 10. 发布门禁

L3 变更只有同时满足以下条件才能发布：

- [ ] 变更声明已评审。
- [ ] 既有功能保护清单全部通过。
- [ ] 云函数、数据库结构、索引和客户端版本兼容。
- [ ] 生产数据已备份并记录备份编号。
- [ ] 体验版真实环境端到端验证通过。
- [ ] 正式版升级路径验证通过。
- [ ] 回滚步骤已演练。
- [ ] 灰度范围和观察时间已确定。
- [ ] `syncLogs`、`conflictLogs` 和错误率基线已记录。
- [ ] 没有未解释的失败、空数据或超时。

任一项未完成，结论只能是“未达到发布条件”，不得以“先发布观察”替代。

## 11. 灰度与停止条件

公共底座变更不得直接全量发布。

灰度期间出现以下任一情况立即停止扩量并回滚：

- 云同步成功率低于发布前基线。
- pending 数持续增长。
- 出现跨账号或跨环境数据。
- 恢复后本地记录减少且无法由用户操作解释。
- 同一 `userHabitId + date` 出现多个最终状态。
- 用户报告打卡成功后重新进入变为未完成。
- 日志无法解释服务端最终状态。

## 12. 正式数据维护规则

- 所有维护动作默认 dry-run。
- 执行前必须导出目标账号相关集合。
- 只能依据逐条证据 manifest 修复。
- 不得根据累计次数推断具体打卡日期。
- 不得伪造未知时间。
- 冲突记录必须逐条授权覆盖。
- 修复必须写 operation 和审计记录，不得直接无痕改最终状态。
- 修复后必须再次 dry-run，证明没有遗漏和重复。

## 13. 责任与复盘

L3 变更必须明确四个角色，可以由同一人兼任，但不能缺失：

- 实施负责人：完成变更与自测。
- 影响审查人：确认依赖链和既有功能保护清单。
- 发布负责人：确认部署、备份、灰度和回滚。
- 数据负责人：确认生产数据无异常。

事故发生后，复盘关注系统和流程，不以个人归责替代治理改进。
