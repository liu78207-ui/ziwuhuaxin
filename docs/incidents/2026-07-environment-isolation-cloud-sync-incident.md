# 2026 年 7 月环境隔离导致云同步失效事故复盘

## 1. 结论先行

这次事故不是“环境隔离和云同步碰巧互相影响”，而是环境隔离的实现直接改进了云同步主链路。

原本云同步只需要回答：

> 这条打卡应该如何可靠地写入云端？

环境隔离改造以后，每一次登录、打卡、取消、习惯同步和数据恢复还必须先回答：

> 当前是什么版本？应该调用哪个云环境？应该读写哪一组集合？

这三个新判断被加入了公共云调用入口和所有核心云函数。一旦其中任一判断、部署或数据准备不一致，全部云同步功能都会受影响。

因此，本次事故的本质是：

> 一项涉及公共基础设施的高风险改造，被当作普通功能改动实施和验收；我们验证了“环境能否区分”，却没有充分验证“区分环境以后，原有完整业务链路是否仍然成立”。

## 2. 发生了什么

事故前，开发版、体验版和正式版使用同一套无前缀集合，例如：

- `users`
- `user_habits`
- `daily_checkin_states`
- `checkin_operations`

环境隔离改造后，路由规则变成：

| 小程序版本 | 数据位置 |
|---|---|
| 开发版 | `test_` 前缀集合 |
| 体验版 | `test_` 前缀集合 |
| 正式版 | 原有无前缀集合 |

这个变化表面上只是“换一个数据位置”，但实际提交同时修改了 49 个文件，包括：

- 小程序启动和登录。
- 公共 `cloudService`。
- `syncCheckin`、`syncHabit`、`recoverData` 等核心云函数。
- 本地 pending 重试链路。
- 数据清理与维护函数。
- 各页面的环境识别。

这已经不是一个独立功能，而是一次横跨客户端、云函数和数据库的同步协议变更。

## 3. 为什么会导致云同步失效

### 3.1 数据地址改变了，但旧状态没有一起隔离

云端集合被区分成测试和正式两组，但本地缓存、登录态和 pending 队列当时没有同时绑定：

- 当前用户身份。
- 当前运行环境。
- 操作创建时的数据目标。

这意味着设备里已有的登录态和待同步操作，不知道自己属于测试环境还是正式环境。版本切换后，它们可能被发送到另一组集合，也可能因为目标集合为空而得到错误的恢复结果。

环境隔离只完成了“云端数据分开”，没有完成“身份、缓存、队列、恢复全过程分开”。

### 3.2 启动时相信旧登录缓存，没有重新确认当前环境身份

当本地已有用户缓存时，启动使用 `login({ force: false })`，可以不访问云端而直接采用旧身份。

在没有环境隔离时，这个优化通常没有问题；加入环境隔离后，旧身份可能来自另一个运行环境。客户端却继续执行恢复和 pending 同步，导致身份确认与数据路由脱节。

### 3.3 测试集合不存在时，被当作“用户没有数据”

环境隔离后的 `recoverData` 对缺失的 `test_` 集合返回空快照，而不是把“环境尚未准备完成”视为发布错误。

这会混淆两个完全不同的情况：

1. 环境部署正确，用户确实没有数据。
2. 环境部署或集合准备不完整，程序读不到本应存在的数据。

系统无法区分两者，后续恢复逻辑就可能把基础设施故障当成正常空用户。

### 3.4 恢复流程会覆盖本地状态并清空 pending

当时的恢复逻辑收到云端快照后，会分别覆盖本地习惯、策略和每日状态，并无条件清空 pending。

如果云端因为环境路由或部署问题返回了空数据或不完整数据，客户端没有 staging、完整性校验和回滚能力。本地尚未确认写入云端的操作也可能失去最后一份恢复依据。

这使“同步暂时失效”被放大成“用户看到数据消失”。

### 3.5 环境参数进入了每个业务云函数

客户端在每次云函数调用中传入 `__runtimeEnv` 和 `__collectionPrefix`，云函数据此拼接集合名。

这带来两个问题：

- 环境路由代码分散在多个云函数，任何遗漏或版本不一致都会造成部分链路读正式集合、部分链路读测试集合。
- 客户端参数本质上不可信。同一个 CloudBase 环境内用前缀隔离，只是逻辑分组，因此更需要防止路由参数遗漏、串用或被旧版本误解释。

项目当前受免费额度限制，只能使用一个 CloudBase 环境，因此“不同集合名”本身不是错误。问题在于同一个业务云函数根据客户端传入的前缀动态决定写入位置。

在单一 CloudBase 环境约束下，更稳妥的实现是：

- 正式版继续调用原有正式云函数，云函数内部固定使用无前缀集合。
- 开发版和体验版调用独立的测试入口，测试入口内部固定使用 `test_` 集合。
- 正式入口和测试入口可以复用同一个业务处理模块，但集合命名空间必须由服务端入口固定注入，不能由普通业务请求自由传入。
- 环境隔离改造优先新增测试旁路，不重写已经稳定的正式入口。

## 4. 为什么原有功能没有被保护住

### 4.1 对改动性质判断错误

我们把这次工作理解成“新增环境隔离”，实际却是“重写云同步的数据路由协议”。

凡是修改下列模块，都不是普通功能改动：

- 环境配置。
- 登录和用户身份。
- `cloudService`。
- `storageService`。
- `syncService`。
- `recoverData`。
- 数据库集合名、索引或权限。
- 小程序启动顺序。

这些模块是所有业务共同依赖的底座。修改底座，影响范围默认是全产品。

### 4.2 测试只证明新逻辑存在，没有证明旧链路不变

当时新增的测试主要证明：

- develop 和 trial 能映射到测试环境。
- release 能映射到正式环境。
- 云函数能访问带 `test_` 前缀的集合。
- 测试集合不存在时可以自动创建或返回空数据。

但缺少决定发布安全的完整回归：

- 正式版升级前已有数据，升级后能否继续同步。
- 体验版和正式版来回切换后，pending 是否仍属于正确环境。
- 本地已有旧登录态时，是否会重新确认环境身份。
- 测试集合缺失与真实空用户能否区分。
- 云端恢复失败或不完整时，是否保持原本地数据。
- 云函数前后端版本不一致时，是否自动阻止发布。
- 真机和真实 CloudBase 环境中，打卡、取消、恢复是否形成闭环。

单元测试通过，只能说明局部代码符合预期，不能证明一次跨端协议改造可以安全发布。

### 4.3 一次提交混入了过多不同目标

同一次变更还包含习惯排序、页面标识、用户资料兼容、数据清理等内容。环境隔离的风险被大量无关改动稀释，难以单独审查、验证和回滚。

基础设施改造必须保持单一目标，否则事故发生后也难以快速确定回滚范围。

### 4.4 缺少发布门禁和回滚证据

发布前没有强制要求同时提供：

- 生产数据备份编号。
- 三个版本的真实环境冒烟记录。
- 旧版本到新版本的升级验证。
- 云函数和客户端兼容矩阵。
- pending 不丢失证明。
- 恢复失败不覆盖证明。
- 灰度观察指标。
- 可立即执行的回滚方案。

因此，“代码测试通过”被错误地当成了“可以安全发布”。

## 5. 根因分层

### 直接原因

环境路由改变了同步数据的目标位置，但身份、本地缓存、pending、恢复和部署没有作为一个整体同步升级。

### 技术根因

- 环境隔离侵入所有云同步业务函数。
- 同一 CloudBase 环境内用集合前缀承担环境边界。
- 缓存和 pending 没有绑定用户与运行环境。
- 恢复不是先校验、后原子替换。
- 环境未准备好与用户确实无数据使用了相同结果。

### 流程根因

- 没有识别出这是最高风险的公共底座变更。
- 没有先定义“原有功能必须保持不变”的验收清单。
- 没有真实环境的端到端回归和灰度门禁。
- 没有要求基础设施改造独立发布和独立回滚。

### 管理根因

我们关注了“新功能是否完成”，没有建立“既有能力是否被完整保护”的工程责任制。

这不是某一个开发人员的疏忽，而是项目缺少变更影响治理制度。

## 6. 当前整改应如何理解

当前工作区已经出现以下整改方向：

- 每次启动强制向云端确认身份。
- 缓存和 pending 绑定 `ownerUserId` 与 `runtimeEnv`。
- 环境不匹配的 pending 隔离，不允许上传。
- 恢复先拉取完整分页并校验，再通过 staging 原子替换。
- 恢复不得无条件清除未确认 pending。
- 同步增加事务、唯一索引、服务端 revision 和冲突日志。
- 清缓存前先处理未同步操作，失败时保留原缓存。

这些都是正确方向，但在完成真实 CloudBase 验证、部署和灰度之前，只能称为“整改候选”，不能宣称事故已经彻底解决。

## 7. 当前约束下的目标架构

当前腾讯云免费额度只提供一个可用 CloudBase 环境。本项目继续采用“同一云环境、不同集合名”，但将正式链路与测试链路在入口上隔离：

```text
开发版 / 体验版
  -> 测试云函数入口
  -> 服务端固定 test_ 集合

正式版
  -> 正式云函数入口
  -> 服务端固定无前缀集合

两类入口
  -> 复用同一业务同步核心
  -> 保持相同 schema、索引和返回协议
```

关键原则：

- 不要求购买第二个 CloudBase 环境。
- 环境由发布配置选择对应的固定云函数入口。
- 正式入口沿用已稳定链路；新增隔离能力优先在测试入口旁路实现。
- 集合前缀由服务端入口固定，不由普通业务 payload 决定。
- 各环境保持同一数据结构、索引和云函数版本。
- 环境切换不得迁移或复用另一环境的本地 pending。
- `test_` 集合是逻辑隔离，不宣称具备独立云环境的物理安全边界。

如果未来具备多个 CloudBase 环境额度，可以再评估物理隔离；这不是当前整改的前置条件。

## 8. 本次事故带来的核心教训

> 修改公共底座，就是修改所有依赖它的功能。

“没有主动修改某个页面”不代表该页面不会受影响。只要修改了它依赖的登录、环境、缓存、同步、时间、数据库或恢复链路，就必须把它当作受影响功能重新验收。

未来不能再以“本次只是新增一个功能”为理由跳过全链路回归。
