# 客户端全量分页恢复变更声明

## 变更目标

所有账号在清缓存、换设备或本地核心缓存缺失后，均可分页恢复全部云端历史；只有完整快照校验成功后才替换本地缓存。

## 不允许改变的既有行为

- 旧客户端未传恢复协议版本时，`recoverData` 继续保持默认最近 90 天和原返回字段兼容。
- 正式版只读取正式集合，开发版和体验版只读取 `test_` 集合。
- openid 只由云函数微信上下文获取。
- 打卡、取消、习惯、策略和报表口径不改变。
- pending、checkinOperations 和客户端序列号不得因恢复或清缓存丢失。
- develop/trial 不得读取正式版无前缀缓存或接管正式 pending；release 缓存 key 保持不变。
- 任一分页、校验或本地提交失败时，已有缓存不得被半份快照覆盖。
- 正式环境本地已有业务数据时，全空云端快照不得自动覆盖本地缓存。
- 云端既有的孤儿策略或每日状态属于历史事实，结构有效且无重复时原样保留；
  不得因旧关联缺失而丢弃记录或阻断整个账号恢复。

## 影响与回滚

- 直接修改：`recoverData`、`syncService`、`storageService`、`cacheService`。
- 间接影响：app 启动恢复、归藏页清缓存、首页和观心页恢复后刷新。
- 数据模型：云端集合和业务字段不变；恢复响应新增协议 v2 `snapshotMeta`。
- 缓存：新增 recovery staging 和 transaction 临时键；develop/trial 业务缓存使用 `test:` 前缀，release 继续使用原 key；成功或可回滚失败后自动清除。
- migration、状态机、报表口径：不变。
- 最坏结果：全量恢复被安全拒绝，用户继续看到旧缓存或无缓存时看到恢复失败。
- 回滚：先回滚客户端，再回滚 `recoverData`；数据库无需反向迁移。

## 发布顺序

1. 将同源代码部署为 `recoverDataV2Test`，开发版和体验版仅通过该函数读取 `test_` 集合。
2. 在开发版、体验版验证协议 v2 全量分页。
3. 备份生产配置并部署向后兼容的正式 `recoverData`。
4. 发布新客户端并灰度观察恢复错误率、分页数和快照校验失败。
5. 任一账号恢复后记录减少或出现重复状态，立即停止灰度并回滚客户端。

## 跨环境缓存修复

- `1.0.1` 体验验证发现，同一微信账号从 release 切换到 trial 时会先显示无前缀正式缓存，清缓存后才显示 `test_*` 云端数据。
- 修复后测试环境只访问 `test:` 本地缓存，正式环境继续使用原缓存 key，不为线上用户执行缓存迁移。
- 新 pending 写入 `runtimeEnv`；测试环境拒绝未标环境或归属不一致的 pending，正式环境仅兼容接管旧版未标环境 pending。
- 本修复不复制、修复或删除任何账号的云端数据；当前 `1.0.1` 不进入审核，重新上传 `1.0.2` 体验验证。

## 测试环境验证记录

- `recoverDataV2Test` 与本分支 `recoverData` 源码 SHA-256 一致，函数超时均为 30 秒。
- 在 `test_daily_checkin_states` 临时写入 501 条唯一标记记录后，
  协议 v2 共恢复 538 条状态、6 页、538 个唯一 `userHabitId + date`。
- 同一数据集使用旧调用形态只返回最近 90 天的 37 条状态，未返回临时远期历史。
- 客户端安全清缓存从本地 15 条恢复为云端 538 条，完整提交后无 staging 或 transaction 残留。
- 501 条临时记录已全部删除；再次恢复后测试账号回到 37 条状态基线。
- 测试集合既有 5 条孤儿每日状态均被保留，未删除或改写。
