# 版本行为分析

本文档针对 `docs/版本分析.txt` 中提出的 4 个问题逐条分析。每个问题从四个维度回答：

- 动作：哪些 service 会被调用、哪些状态机会流转。
- 案台（`miniprogram/pages/home/home.js`）：首页今日列表如何变化。
- 观心（`miniprogram/pages/stats/stats.js`）：周/月/年报表如何变化。
- 数据处理：本地缓存、operation 流水、pending 队列、云端同步、报表口径、特殊日规则。

所有结论都遵循：
- `AGENTS.md` 长期治理规则。
- `docs/architecture/technical-architecture.md` 数据架构与分层。
- `docs/architecture/state-machine.md` 状态机约束。
- `docs/v1/v1-report-rules.md` 报表口径。
- `docs/v1/v1-product-boundary.md` 页面层禁止事项。

## 问题 1：取消打卡会做哪些动作，在案台页面怎么体现，在观心页面怎么体现，数据怎么处理

### 1.1 触发场景

用户在案台首页对今天已经完成打卡的某个习惯再次点击（toggle），由 `checked` 切到 `canceled`。取消必须基于已经存在的 `dailyCheckinState.status === 'checked'`，不允许越过 service 直接改状态。

### 1.2 动作（service 层）

调用链：

```text
home.js handleCheckin
  -> checkinService.toggleCheckin(userHabitId, todayKey)
  -> checkinService.undoCheckin(userHabitId, date)
```

`miniprogram/services/checkinService.js:73-126` `undoCheckin` 内部按以下顺序执行：

1. 幂等检查：读取 `storageService.getDailyState(userHabitId, date)`，如果已经 `canceled` 直接返回，避免重复流水。
2. 校验习惯：调用 `habitService.getHabitByUserHabitId(userHabitId)`，必须存在且当前 `active`。`active` 是后续 `policyVersionId` 解析的前提。
3. 缺省补齐：若 `existingState` 为空，构造一条 `unchecked` 状态写入 `dailyCheckinState` 作为占位。这一步是 PRD 不允许“物理删除历史记录来表达取消”的实现。
4. 生成 operation：
   - `clientSequence = storageService.getNextClientSequence()` 持久化序列号，保证同毫秒下也能排序。
   - `operation = createUndoOp(userHabitId, habit.habitId, date, clientSequence)`，对应 `models/checkinOperation.js` 中的 `OPERATION_ACTION.cancel`。
   - 关键字段：`operationId`、`idempotencyKey`、`date`、`action='cancel'`、`createdAt`、`userHabitId`、`habitId`。
   - `idempotencyKey` 由 clientSequence + 原子盐生成，重复提交只命中一次。
5. 落库 operation：`storageService.saveCheckinOperation(operation)`。
6. 更新 `dailyCheckinState`：调用 `createCanceledState(userHabitId, habit.habitId, date, operation.operationId)` 覆盖原 state，`status='canceled'`、`canceledAt=now`、`lastOperationId=operation.operationId`。
7. 入 pending 队列：`syncService.pushWithDedup('checkin', 'undoCheckin', { ... action: 'undo', idempotencyKey, clientCreatedAt, clientSequence })`。
8. 通过 `EventBus` 广播 `checkin:updated`（由 `syncService` 内部或 storage 写入层触发）。

以上流程没有走 `wx.cloud.callFunction`，没有 `wx.setStorageSync`，没有 `new Date()` 计算业务日期，全部由 service 完成，符合 AGENTS.md 第 3、4 节。

### 1.3 案台页面体现

`miniprogram/pages/home/home.js:122-171` `handleCheckin` 收到 toggle 后的影响：

- 防抖 1 秒：`processingHabitId` 锁同 habit，重复点击无效，避免 `checked` ↔ `canceled` 反复横跳。
- 调用 `checkinService.toggleCheckin`，乐观更新由 service 完成（`storageService.setDailyState` 同步落本地缓存）。
- 重新拉取：`await this.loadViewModel()` → `homeService.getHomeViewModel()`：
  - `homeService.getHomeViewModel` 通过 `habitService.getTodayHabits(todayKey)` 读取 `active` 实例。
  - 再用 `checkinService.getDailyStatesByDate(todayKey)` 取得 `todayStates`。
  - 任务卡 `isChecked` 来自 `state.status === 'checked'`，取消后 `isChecked=false`，圈圈从完成态回到未完成态。
  - `checkedCount`、`totalCount`、`progressPercent` 自动重算：取消一个会让 `checkedCount -1`、百分比下降。
- Toast 提示：'`已取消打卡`'。
- 自定义 TabBar `selected=0` 已在 `onShow` 设置，不受 toggle 影响。

UI 表现总结：
- 任务卡视觉上立刻从“完成”回到“待完成”。
- 顶部进度数字（`progressPercent`）立刻回退。
- 时辰区块（`timeInfo`）和底部导航不受影响。
- 网络异常时，state 已经本地落库，UI 与本地一致；pending 队列里的 `undo` 流水会由 `syncService` 在网络恢复后补推，云端 `daily_checkin_states` 最终也会变成 `canceled`。

注意：

- 案台不会展示“打卡流水”或“最近一次操作”之类调试信息，符合 V1 边界。
- 如果 `dateConfidence=low`，home 不会显示单独提示，仍按 service 返回渲染；`reportDebugLogs` 记录原因。
- 案台不会去重算 streak，streak 由 `reportService` 在切到观心时计算。

### 1.4 观心页面体现

`miniprogram/pages/stats/stats.js` 不直接计算报表，调用 `reportService.getWeeklyReport | getMonthlyReport | getYearlyReport`。

取消打卡对观心报表的影响按 `v1-report-rules.md` 第 5、6 节口径执行：

1. 当日（今日所在自然日）状态：今日（如果不是未来日期）原本是 `checked`，取消后变 `canceled`。
   - 普通应修日：`canceled` → 分母 +1、分子 +0。
   - 不应修日：原本就 `not_required`，canceled 后仍 `not_required`（一般不会发生，因为不应修日不会进入打卡入口）。
2. 周报 7 天点阵：今日单元格从“已完成”切到“应修未完成”。
3. 月历：今日格子状态从 `checked` 切到 `unchecked`（或带取消标记的灰态）。
4. 年热力图：今日所在格分档从 `high` 降到 `low` 或 `medium`（按当天累计完成率分档）。
5. 周/月/年完成率：分子 -1，分母不变，比率下降。
6. Streak：如果取消是发生在 streak 末端那一天的取消，streak 不会跨过 `canceled` 自然日继续累计。`reportAggregator` 计算 streak 时按“自然日内至少有一项有效应修且 checked”作为连日条件。
7. 同 `habitId` 多个 `userHabitId` 聚合：本 habitId 下其他实例状态不变，聚合分子减少 1。
8. 未来日期：本场景必为今日或过去日期，不存在 `isFutureDate` 干扰。
9. 低可信日期：若本条 operation 命中 `dateConfidence=low`，按 v1-report-rules.md 第 14 节，本日不计入分母也不计入分子，但日历仍会显示为 `pending` 或异常标记。

观心页面交互层：
- 顶部 `dataVersion`、`reportVersion` 失效：service 内部对 `reportCache` 做失效（或下次进入时重算），避免用户看到陈旧数据。
- `stats.js` 的 `onShow` 会调用 `getCurrentReport()`，重新跑一遍 `reportService`。
- 缓存命中由 `cacheMeta` + `reportVersion` 控制，打卡类操作后通过 `EventBus` 的 `report:updated` 触发刷新。

### 1.5 数据处理

#### 1.5.1 本地数据

- `dailyCheckinState` 表：
  - 同一 `(userHabitId, date)` 的 state 由 `checked` 改为 `canceled`。
  - `lastOperationId` 更新为本次 `undo` operation 的 `operationId`。
  - `canceledAt = now`（ISO 时间戳）。
  - `updatedAt` 重写。
  - 状态机流转：`checked -> canceled`（合法），不删除历史。
- `checkinOperations` 表：
  - 追加一条 `action='cancel'` 记录。
  - `idempotencyKey`、`operationId` 不可变。
  - `clientSequence` 单调递增，retry 时保留原 key。
- `pendingOperations`（同步队列）：
  - `pushWithDedup('checkin', 'undoCheckin', payload)` 进入队列。
  - payload 含 `userHabitId / habitId / date / policyVersionId / operationId / idempotencyKey / action: 'undo' / clientCreatedAt / clientSequence`。
  - 网络异常或离线时滞留，UI 已有即时反馈。
- `cacheMeta`：
  - `dataVersion` 自增（或由 storageService 内部版本号管理）。
  - `reportVersion` 触发失效，下次进入观心时重算。
- 旧 `CheckinLogs`：V1 不再作为事实源，但仍可能在迁移期出现，service 不会再写它。
- 旧 `MyHabits`、`userStrategies`：无变化。

#### 1.5.2 状态机与字段约束

依据 `state-machine.md` 第 4、5 节：

- `checkinOperation` 状态：`pending`（本地生成即 pending），后续 `syncService` 改为 `synced` 或 `failed`。
- `dailyCheckinState` 状态：`checked -> canceled` 合法。
- `syncStatus`：由 `syncService` 或云端确认回写。页面层禁止把 `pending` 直接改 `synced`。

`AGENTS.md` 第 6.1 节强约束：取消不得通过物理删除历史记录来表达。`undoCheckin` 通过追加 operation + 改 final state 表达，是合规实现。

#### 1.5.3 云端同步

`syncService` 在以下时机消费 pending：

- `App.onLaunch` 或首页 `onShow` 检测到网络恢复。
- `wx.getNetworkType` 变化事件回调。
- `syncService.syncPendingOperations()` 主动调用。

执行流程：

1. 按 `clientSequence` 升序取出 `checkin / undoCheckin` 流水。
2. 调用 `cloudService.callFunction('syncCheckin', payload)`：
   - 入参：`operationId / idempotencyKey / userHabitId / habitId / policyVersionId / date / action='undo' / clientTime / timezone`。
   - `cloudfunctions/syncCheckin` 必须按 `idempotencyKey` 幂等 upsert。
   - 重复请求不会放大计数；同一 `operationId` 二次提交只回放一次。
3. 云端写入 `checkin_operations` 一条 `cancel` 记录，更新 `daily_checkin_states` 中 `(userHabitId, date)` 的 `status='canceled'`、`lastOperationId`、`canceledAt=serverTime`。
4. 成功后 `syncStatus` 改 `synced`，`sync_logs` 记录成功。
5. 失败：保留 `pending` 状态，按 `retryPolicy` 重试；多次失败进 `failed`，进入 `conflict_logs`，由 `syncService.retryPendingOperations` 重新置为 `pending`。
6. 多端冲突：若另一端已经把同日改为 `checked` 且 `clientCreatedAt` 更晚，遵循 `AGENTS.md` 第 9 节“服务端最终归并、保留冲突日志”原则。

#### 1.5.4 报表口径再确认

- 今日是普通应修日：分子 -1，分母不变。
- 今日是策略修改当天且之前已打卡：按 `state-machine.md` 第 5.4 节 `lockReason='strategy_changed_after_checkin'`，但用户后续取消后最终状态是 `canceled`，按 `v1-report-rules.md` 第 7 节“修改前已打卡，但随后取消当日打卡，该日不计入分母和分子”，分子分母同时 -1。
- 今日是删除当天且之前已打卡：同上口径，分子分母同时 -1。
- 同 `habitId` 存在多个 `userHabitId`：仅本实例分母分子变化；展示层聚合视图会少 1。

### 1.6 验收要点

- 案台：`isChecked=false`，`progressPercent` 自动重算，Toast “已取消打卡”，无网络阻断。
- 观心：今日单元格由 `checked` 变 `unchecked`/`canceled`；月历当日降档；年热力图降档；周/月/年完成率下降；streak 不跨过 canceled 日。
- 数据：保留历史 `checked` operation，追加 `cancel` operation，`dailyCheckinState` 流转 `checked -> canceled`；`pending` 队列入队；`syncCheckin` 幂等回放；`dataVersion` 与 `reportVersion` 同步失效。
- 不允许物理删除 `checkin_operations` 中的 `checkin` 记录来表达取消。
- 取消后再次点击会从 `canceled` 回到 `checked`，必须生成新的 `checkin` operation，不能复用旧 `idempotencyKey`。

## 问题 1 缺陷：观心页 7 天点阵全部置灰分析

### 现象

- 案台：晨起温水今日打卡成功 → 取消打卡，案台 `isChecked` 正确变 false，Toast "已取消打卡"。
- 观心：进入周报后，晨起温水这一行的 7 个圆点全部呈浅灰色（与默认未应修一致），而不是仅今日从“已完成”变“应修未完成”。

### 原因分析

#### 1. 数据层输出值与样式层枚举不一致（主要原因）

- `miniprogram/services/reportAggregator.js:45-53` 定义的状态枚举：
  ```text
  DAY_STATUS = {
    checked, unchecked, canceled,
    not_required, future, low_confidence, partial
  }
  ```
- `resolveReportDayStatus` 在“应修日”分支对 canceled 状态返回：
  ```js
  if (finalStatus === DAY_STATUS.canceled) {
    return {
      status: DAY_STATUS.canceled,
      isDue: true,
      contributesDenominator: true,
      contributesNumerator: false,
      reason: 'canceled',
      ...
    }
  }
  ```
  其他 6 天无 `dailyState` 时走 `unchecked` 分支。

- `reportService.adaptToLegacyFormat` 透传 `day.status` 到 viewModel。

- `miniprogram/pages/stats/stats.wxml:46` 渲染：
  ```html
  <view class="wt-dot {{day.status}} {{day.themeClass}}" ...></view>
  ```

- `miniprogram/pages/stats/stats.wxss:225-261` 现有规则：
  ```css
  .wt-dot            { background: #F4F6F8; border: 2rpx solid transparent; }
  .wt-dot.checked    { background: var(--theme-color, var(--c-primary)); border: 2rpx solid var(--theme-color, var(--c-primary)); }
  .wt-dot.unchecked  { background: #FFFFFF; border: 2rpx solid var(--theme-color, var(--c-primary)); }
  .wt-dot.inactive   { background: #F4F6F8; border: 2rpx solid transparent; }
  .wt-dot.deleted    { background: #F4F6F8; border: 2rpx solid transparent; }
  ```

- 缺规则：`wt-dot.canceled`、`wt-dot.not_required`、`wt-dot.future`、`wt-dot.low_confidence`、`wt-dot.partial`。
  - 这五个状态值落到 `.wt-dot` 默认样式 = `#F4F6F8` 浅灰 + 透明边框。
  - 与 “未应修 / 删除后” 视觉无差。
  - 今日 cancel 后本应是 “应修未完成”，视觉上应等同于 `unchecked`（白底 + 主题色描边），但实际显示与未应修一致 → 看上去就是“置灰”。

#### 2. 取消当天本应是 “应修未完成” 而不是 “未应修 / 已删除”

- `v1-report-rules.md` 第 5 节规定：普通应修日 `canceled` → 分母 +1、分子 +0，UI 应展示“应修未完成”态。
- 现在因为没有 `wt-dot.canceled` 规则，退化成默认 `.wt-dot`，视觉上与“未应修”相同，违反报表口径对“应修未完成”的视觉约定。

#### 3. “全部置灰” 现象的具体拆解

- 取消今日时，`buildDayVerdicts` 输出的 7 天 `status`：
  - 今天：`canceled`（无 CSS → 浅灰）。
  - 其他 6 天：`unchecked`（白底 + 主题色描边，理论应可见）。
- 但因为 `wxss` 没有 `wt-dot.canceled` 规则，今天的浅灰看上去与 `inactive` / `deleted` 不可区分；尤其在主题色描边宽度很小、屏幕缩放下，6 个白底浅描边的 `unchecked` 点容易被用户视觉合并为“全灰一排”。
- 若用户实际看到“全部置灰”，还存在另外两类次要原因：
  1. **多实例合并 + 旧实例全 `not_required`**：旧 userHabit 已 `deleted` 且 `deletedAt <= weekStart`，则其 7 天全是 `not_required`（无 CSS），与今日 cancel 实例的两行视觉上叠加成一片灰。
  2. **策略版本找不到**：`fetchPolicyVersionsByUserHabitId` 返回空数组，`resolveEffectivePolicyVersion` 返 null，7 天全是 `not_required`（no_policy_version）。这通常由迁移期或同步回写缺失导致。

#### 4. 验收 `__tests__/unit/services/reportAggregator.test.js` 已证明数据层正确

- 测试 `包含 checked/unchecked/canceled 状态的日正确映射` 验证 verdict 输出的 `status` 字段是 `DAY_STATUS.canceled`、`DAY_STATUS.unchecked`、`DAY_STATUS.checked`。
- 即数据层 `day.status = 'canceled'` 没问题，问题完全在 WXML/WXSS 缺失样式枚举。

### 复现步骤与诊断路径

1. 复现：
   - 案台：晨起温水打卡。
   - 案台：再次点击晨起温水（取消）。
   - 观心：进入周报。
   - 观察：晨起温水 7 个圆点。

2. 数据诊断（无需改代码）：
   - `wx.getStorageInfoSync` → 取 `dailyCheckinStates`。
   - 过滤 `userHabitId === uh_17_xxx`、`date` 落在本周。
   - 预期：只有 1 条记录（今日），`status === 'canceled'`；其他 6 天无记录。
   - 若发现多条 canceled 记录或旧 userHabit 残留 → 走“多实例合并”分支。
